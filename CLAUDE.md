# Trains vs Spaghetti — BACKEND (game server)

Frontend (3D client) lives at `../Trains-vs-spaghetti`. Colyseus + Mongo, started from the Bowling Roll server and reshaped for this game.

- `npm start` (tsx watch, port 2567), `npm run build` (tsc -> `build/`), `npm test` (mocha + `@colyseus/testing`, Mongo faked via `__setPlayersForTest`; tests share one booted server, `test/server.ts`). Node >= 22.
- One room, `world` (`src/rooms/WorldRoom.ts`, client calls `joinOrCreate("world", { userId, username, pfp, pose, loadout, avatar })` through the Bloxity matchmaker endpoint, `Legion.SDK.net.resolveEndpoint`). Client-authoritative: the server only bounds/sanitises saves (`src/sanitize.ts`). `src/db.ts` degrades to "no persistence" when `MONGODB_URI` is unset/unreachable; guests (`guest-` ids) are never saved. `/health` for Legion; `/monitor` and the playground are dev-only. `ROOM_MAX_CLIENTS` (constants.ts) is the room size and the deploy `roomSize`.
- **No gems**: premium currency goes through the Bloxity platform (`gems.requestPurchase`), nothing about it is stored here; `saveProgress` drops a `gems` field.
- Messages client -> server: `saveProgress` (the whole snapshot, debounced client-side), `identify` (`{ userId, username, pfp }` after a sign-in/out mid-session), `pose`, `loadout`, `setAvatar`, `emote`, `action` (see Presence). Server -> client (private): `progress` (the saved doc, sanitized), `noProgress` (new account, guest, or no database: the client keeps its fresh state and saves it), `serverError` (the save could not be read: saving stays off so it is never overwritten), `leaderboard`. Saves are ignored until the session's load has answered (`loaded`). A second live session on the same account is evicted.
- Saved progress (`PlayerDoc`, client `game.js` `SAVED`): `power`, `level`, `xp`, `wins`, `rebirths`, `playtime` (s), `titlesOwned[]`/`title` (equipped must be owned, "" = none), `railcars[] { uid, type }`, `nextUid`, `singles[]`, `stock { period, bought }`, `quests { day, progress, claimed }`, `settings` (bool map of the in-game Settings toggles), `trainsOwned[]`/`train` (shop train indices, `DISPLAY_TRAINS` row by row; equipped must be owned), `lastSeen`; plus `username` and `pfp` taken from the connection's own roster entry. Spin wheel / daily reward / pets of the old game are gone (quests reset client-side on the UTC day).
- Leaderboards (`src/leaderboard.ts`, `test/Leaderboard.test.ts`): the hub's boards. Top `LEADERBOARD_SIZE` saved players by each of `LEADERBOARD_STATS` (`rebirths`, `wins`, `power`, `playtime`), read with find/sort/limit into one process-wide cache refreshed at most every `LEADERBOARD_EVERY_MS`; each player's own rank = countDocuments(stat > theirs) + 1 (null for guests / no score). Server -> client `leaderboard` { boards: { stat: [{ name, value, pfp }] }, ranks: { stat: n | null } }, sent after each load and to everyone every `LEADERBOARD_EVERY_MS` (room clock). The client submits the same four stats to the Bloxity portal's own boards (`Legion.SDK.leaderboard.define/submit`), so the in-game boards and the portal's are two views of one score.
- Presence (`src/presence.ts`, `test/Presence.test.ts`): what the others draw, relayed through the roster as sent, only bounded. Roster fields `uid` (public Bloxity id, `guest-…` for guests: matches a Bloxity chat message's `userId` so chat bubbles land on the right train), `username`, `signedIn`, `pfp`, `x`/`y`/`z`, `yaw`, `speed`, `train` (shop index), `title`, `level`, `railcars` ("type,type", at most `PRESENCE_RAILCARS_MAX`), `training`, `avatar` (Bloxity look JSON `{ equipped, proportions, skin }`, at most `AVATAR_MAX_LEN`, never parsed: every client dresses the driver in the cab with it, so everyone sees everyone's skin), `emote` + `emoteSeq` (Bloxity emote catalogue id being played, "" = stopped; the seq bumps on every start so repeats arrive) and `action` + `actionSeq` (one-shot game action slug such as `smash`, `horn`, `levelUp`, `steal`). Messages `pose` { x, y, z, yaw, speed } (~10/s, `POSE_BOUNDS`), `loadout` { train, title, level, railcars: [type], training }, `setAvatar` { avatar }, `emote` { id }, `action` { name }; emote/action broadcasts are rate-limited per player (`BROADCAST_MIN_MS`). The join options may carry `pose`, `loadout` and `avatar` too. Chat itself is Bloxity's (SDK `chat.onMessage` on every client), the server only supplies the uid mapping.
- `src/constants.ts` bounds must cover the client's `src/config.js` (ids match `ID_PATTERN`; currency up to 1e33). A contract change goes in both projects.
- CI/CD: `.github/workflows/deploy.yml` tests on PRs and pushes to `main`/`dev`; pushes also build+push a GHCR image and deploy to Bloxity Legion (`main` = prod, `dev` = dev), sending `roomSize` = `ROOM_MAX_CLIENTS` read from `src/constants.ts` (keep it 2-100 for party play; no `seatCap`: the matchmaker sizes pods). Needs repo var/secret `LEGION_GAME_ID` (the slug registered on the Bloxity dashboard; the client's `GAME_SLUG`) and secret `LEGION_DEPLOY_TOKEN`.
